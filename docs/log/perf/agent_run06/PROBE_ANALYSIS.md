# run-06：全部 probe 轨迹的语义审计与低成本停止候选

日期：2026-09-10。基于本轮 13 个真实介入请求、24 次 probe，以及 [RESULT.md](RESULT.md) 的完整关联。目标是**在恰当位置结束思考，保留合格答案/下一步工具动作，同时减少试答、重复 prefill 和重复生成的成本**。

标题请求的端到端时延改善属于有效收益，不因 `auxiliary` 身份排除。单独报告标题请求 E2E，同时继续报告完整 Agent task wall；二者不等额相加，只是防止重叠请求重复计时，不是否定标题优化的价值。

## 1. 结论：可以优化，但“降低阈值”和“缩短 trial”解决不同问题

**后续实验决策（2026-09-10）**：用户选择先只给原 trial cue 追加 `</think>`，不同时扫描 gate 或 trial 长度。已准备 [单变量实验 patch、输入及步骤](trial_close_experiment/README.md)；生产源码尚未应用。下列多轴候选保留为该实验之后的分析方向，不作为当前执行顺序。

本轮最有价值的优化入口是标题：8 条介入标题均出现**已经提出合适标题、后续没有新增必要信息，却反复比较近义表达/数长度/宣布准备输出**的现象。它们占 19/24 次 probe、42.632/51.142 秒 probe wall。

优先级建议：

1. **先用现有接口验证标题 `.93→.90`，以 `.80` 为探索点**，不要全局直接降低到 `.85`：本轮 `.85` 相比 `.90` 不增加任何标题接受，只多接受一条最终写错 API 的 case 26 请求。
2. **试答改短值得测试，但先对照 20 与 10，不只测 10。** 冻结本轮调用路径的成本模型：50→10 约少 13.390 秒 decode，50→20 约少 9.772 秒；prefill 的 31.472 秒仍在。20 保留本轮全部 8 次自然结束的短 trial；10 会截断其中 4 次。
3. **先确认 probe 输出究竟是什么，再选择置信算法。** 当前 trial cue 和最终答复 cue 不一致，trial prompt 本身没有显式 think-end；`reasoning_ended=True` 不是给模型输入插入 `</think>`。phase 没有 trial 文本或逐 token logprob，不能假定每次都在给同一种“最终答案”评分。
4. **中期更有潜力的是“短试答检查，接受后原 child 继续输出”**，避免已经生成的合格标题被丢弃、又重新 prefill 采样。它需要状态机/输出契约修改，不是 YAML 调参。另一候选是 probe 拒绝后的续想也采用观察旁路，遇到自然 think-end 后不再新建 final child。

本文件是证据分析与候选设计，不是生产参数推荐已验收，也未修改运行时。

## 2. 能从现有数据知道什么

### 2.1 证据分层

- **实测**：每次 probe 的源 prefix token 数、生成长度、mean confidence、Value-Min 原始值、wall/prefill/decode、接受与否；全部对外思考和回答文本。
- **人工语义判断**：标题候选已经足够贴题、后续是低价值润色；代码轨迹是否仍有未解决事实。不是自动 Judge 正确率，也不是“停止后一定得到相同输出”。
- **缺失**：每个 probe 的原始文本/IDs/逐 token logprob、精确切点前后的 source delta 文本映射。不能用最终回答冒充 trial 回答，也不能从一个均值恢复前 10 token 得分。

本机没有目标 tokenizer。下文保留精确 phase token 位置，但**不把对外全文某一句话硬标成第 850 个 token**。最终标题在思考全文中出现的位置是字符偏移，不是 token 切点；精确的“在该 probe 前已完成候选”需要服务器补切点证据。

### 2.2 现有评分到底衡量什么

源码 [confidence.py](../../../../dtb/reasoning/confidence.py) 的平均置信度为：

```text
C = Σ exp(sampled_token_logprob_i) / N
```

这是**当前被采样词序列的平均词概率**，不是“答案正确概率”或“继续思考能改善多少”的概率。标题有许多同样合理的说法，某个词的低概率可能只代表措辞不唯一；代码/JSON 开头的路径、括号、键名高概率也不代表后续实现正确。

24/24 probe 的 `pair_count == generated_tokens`，本轮不存在“缺失 logprob 仍进分母”导致虚低的证据。全部使用 `average_fallback`；这也符合默认 Value-Min 关闭时的正常行为，不能据名字推断故障。

## 5. trial 50→10：省多少，可能失去什么

### 5.1 量化成本

24 次 probe 共 897 token：16 次生成 50 到 `length`，8 次自然 stop，长度为 `9,9,9,10,11,13,18,18`。其中 7 次自然 stop 被拒绝；“生成结束”与“当前 gate 接受”不是同一条件。

冻结调用次数和前缀，以每个 phase 的实际 decode/token 比例线性估算：

| trial 上限 | 预计保留 hidden token | 少生成 token | 估算 decode 节省 | 不变的 prefill |
| --- | ---: | ---: | ---: | ---: |
| 50 | 897 | 0 | 0 | 31.472 s |
| 20 | 417 | 480 | 9.772 s | 31.472 s |
| 10 | 237 | 660 | 13.390 s | 31.472 s |

50→10 约少 73.58% trial token，但只对应原 probe wall 的约 **26.18%**；按不变路径模型，probe wall 约 51.142→37.752 秒，不是减少 80%。标题部分估算省 10.003 秒，主/子 Agent 3.387 秒。50→20 相比 10 只多约 3.618 秒 decode，却保留本轮全部自然完成的短 trial，适合作为对照。

这是成本模型而非实测：batch/首 token、取消尾部、调度变化并非线性；trial 变短后得分和接受次数也可能变化。只删 decode 而不变更接受策略，case 34 这种 3×9-token trial 的浪费完全保留。

### 5.2 更短不天然更准

- 标题 10 token 可能覆盖完整标题，也可能在实体名或第二个主题处截断；本轮 4/8 自然完成的 trial 长于 10。
- 代码/工具前 10 token 可能全是 `<tool_call>`、工具名、JSON key、路径前缀等容易预测内容，还没生成决定行为的参数值。高分不代表后续代码安全。
- 一个低概率关键词在 10-token 均值里权重是 10%，在 50-token 里只有 2%；换长度后 `.93` 不是同一校准尺度。
- 本轮只有总均值，无法知道 `mean10`。不能按 50-token 得分假设 10-token gate 作出同样决定。
- 当前 `DtbAlgorithmPolicy.trial_answer_length=50` 是 [schema.py](../../../../dtb/config/schema.py) 中的 code-owned 不变量，`__post_init__` 拒绝其他值；实际 generation 读取 policy，而不是 scene 的 `check_answer_len`。**把 YAML 的 `check_answer_len` 改为 10 不会实现该实验**；需显式实验实现和新 policy 身份，或在隔离探针 harness 中比较固定前缀，不修改生产默认值。

## 6. 置信算法是否应更换

### 6.1 直接开启现有 Value-Min：不建议作为降成本首选

现有 Value-Min 是过滤部分结构 token 后，取最低 K 个 logprob 的均值再取 exp。phase 已保存 `value_min_raw`，可按其实际窗口重算：**24/24 个 exp(raw) 均低于 .93，连当前两个接受点也不再接受**。

它更偏保守，可能用于防止某些高概率格式掩盖低概率内容，但不能在仍用 `.93` 时改善本轮接受率。改用几何均值、较低分位数同样不能沿用旧阈值。标题的同义措辞本来就可能低概率，最小值类分数还可能放大这一特点。

此外，[token_filter.py](../../../../dtb/reasoning/token_filter.py) 的当前过滤集来自既有 JSON/业务字段约定，不是通用的“语义信息识别器”。不能把“非结构 token”直接叫关键事实，更不能承诺过滤后就完成 Agent 场景校准。

### 6.2 更合适的目标：输出就绪度，而不是选词唯一性

建议先离线比较这些信号，不急于新增一个在线大模型 Judge：

1. **输出形状与完成性**：标题是否非空、单行、≤50 字符、无工具标记、无解释，并且自然结束。形状合法只是必要条件，还要主题匹配；不能仅看到 EOS 就接受任意响应。
2. **内容 token 分数**：区分结构/模板前缀与实体、数值、参数值；记录前 10/20/50 的均值、有效数量、最低分位，而不是仅一个总平均。
3. **语义候选稳定性**：标题主题及约束满足后，只在同义措辞间切换不应视为“仍然未就绪”。可在已经介入的长轨迹上离线标注候选首次可用点，再验证一个轻量特征或分类器是否值得其成本；不要对所有短请求新增全文语义扫描。
4. **剩余价值/成本**：估计继续思考所能改善的质量及可省 token 是否足以覆盖下一次 probe。相邻检查得分并不单调，本轮不能使用简单“连续上升才接受/下降就再想”规则。

评估标签应为“在该前缀停止后，实际得到的标题/下一步动作是否合格”，而不是“该轨迹最终成功”。标题允许语义等价，不要求和 Vanilla 字面一致；代码须编译/DT，单轮回放合法 JSON 不替代质量。

## 7. 两个算法层面的核心检查与候选

### 7.1 先对齐 trial 与真正 final 的输入语义

当前 [generation_states.py](../../../../dtb/reasoning/generation_states.py) 具有以下源码事实：

- trial 输入：`P + H + TRIAL_PROMPT`，后缀为“直接给答案、without explanation、**Final Answer**”，**没有显式 think-end**。
- trial `engine_request_kwargs(..., reasoning_ended=True)` 不改 prompt IDs。[request_context.py](../../../../dtb/reasoning/request_context.py) 只传 kwargs；本地 vLLM 的 [async_llm.py](../../../../third_party/vllm/vllm/v1/engine/async_llm.py) / [request.py](../../../../third_party/vllm/vllm/v1/request.py) 把该值转入结构化输出状态，不插入模型的结构 token。
- gate 接受后，当前实现丢弃试答，再以另一段 `GUIDED_FINAL_CUE_V1` 和 think-end 进入新的 final generate。

**假设**：部分 50-token trial 可能仍是 reasoning/解释/不同格式的答复，而 gate 将其得分用于预测另一种 final prompt 的质量。现有日志没有 trial 全文，尚不能确认这就是低分原因。应先取证，不能直接宣称当前 cue 有 bug。

定向比较三个变体：原 cue；与真实 final 完全一致的 cue+结构 boundary；后者的 20/10-token 检查。除所测后缀/检查长度外保持相同 P/H、sampling 和模型。检查 trial 内是否出现解释/think-end/工具标记，标题何时完整，前 10 token 是否都是格式。这比只扫描 `.93/.90/.85` 更能回答评分对象是否正确。

### 7.2 候选 A：可继续的短试答，接受后晋升为 final

目的：不重复生成已验证的短答案，并减少接受后的新 child prefill。

最小流程：

```text
H 已达到介入条件
→ 以真正 final 的同一 cue/boundary 启动候选 child，先缓冲不外发
→ 10 个 token 首检（仅一个检查点，不是先用 max_tokens=10 强停）
→ 明确接受：将缓冲前缀交给 parser，继续同一 child 输出
→ 不确定：同一 child 继续至 20/上限检查，不重新提交 20-token 请求
→ 明确拒绝：取消并排空候选，隐藏全部候选输出，从原 H 继续思考
```

这是**候选设计**，不是现有函数可直接切换的开关。必要约束：

- trial 与最终模型前缀必须相同；不能把现有不同 TRIAL_PROMPT 的 10-token 文本直接嫁接到 guided-final。
- 不改变 sampling/DP/LoRA 等调用上下文；接受时保持同一个 decoder 流、source IDs 和 text 连续性；拒绝时仍处理取消尾部和 G0 可达边界。
- 短标题在 10–20 token 内自然完成且通过质量/格式 gate，可直接交付完整候选；拒绝的自然 terminal 不泄漏到外部。
- 工具参数只按正常 parser-facing 连续流输出；不能因为前 10 token 合法就认定整段参数合法，也不能在接受前触发工具执行。
- 账本区分“候选曾隐藏、后来可见”和“永久隐藏的拒绝试答”：模型 token 只计一次，completion 额度包含晋升前缀；外部 terminal 恰好一个。性能对比仍保留原生答案成本。
- 晋升需要 child 具有足够的外部剩余额度，不可先硬设 `max_tokens=10` 结束后又称“同 child 继续”。长答复的缓冲/早停/不确定策略须有界。

预期收益来源是减少**调用次数及重复 prefill/生成**，不只是将 50 改 10。当前只接受 2 次，所以仅优化“接受后复用”在原参数下收益有限；需与更有效的就绪判断一起验证，不能预先相加各项估算。

### 7.3 候选 B：拒绝后的续想也原生旁路；限制重复 probe

当前拒绝后 `iterative_think` 仍用固定段长/token-stop；模型自然 think-end 后新建 final。可复用介入观察机制：后续段在检查长度前自然结束思考时，继续同 child 正文，不额外 final handoff；到达下一检查点且仍 OPEN 时才取消/probe。

本轮 11 条 `model_think_end` final 的 prefill 合计 **5.853 秒**，是可审计的候选成本项，不是已证明能全部节省的净时延。该改动需要统一后续段的观察计数、额度、boundary 和终态，不能只删 stop 参数。

另一实验是“最多尝试一次 probe，拒绝后恢复无 probe 的原生续写”，用于判断 repeated probing 的净价值。但**现有 `fixed_num_thinking=1` 不等价**：现代码在最后一次失败 probe 后生成一个 stride，然后强制 final，可能改变质量。若要“少检查但不强停”，必须显式增加状态机行为，不能用 N=1 冒充。

对 case 26 这种缺少 API 证据的循环，更好的下一步可能是让模型尽快查询源码，而非继续重复试答。控制器不应凭一个低分主动编造正确 API、强制执行某个工具或宣称质量保证；此类策略须另做 Agent 行为实验。

## 8. 下一轮最小实验与可执行接口边界

### 8.1 先补“足以选择算法”的数据

选择 8 条介入标题、5 条主/子轨迹，加入同输入下自然短于阈值的 Vanilla 对照。第一轮不跑大网格：

1. 保留当前 50/.93 作为控制，冻结 P 与每个可达 H；记录真正切点 source IDs/text、版本、参数，不从 post-parser reasoning 重新编码伪造 H。
2. 隔离诊断采集每个 trial 的实际输出、逐 token ID/logprob，以及前 10/20/50 的平均分/有效 token 数、结构标记和自然完成位置。raw 文本保存在定向诊断产物，**不把正文塞进常规 phase telemetry**。
3. 数值统计可在 `OBSERVABILITY.mode=phase` 下作为可选派生字段扩展；目前尚未实现。off 不计算这些诊断量、不保存全文。已有 phase 与 stream_audit 是互斥模式，不伪造“phase+stream_audit”配置；原始流另做相同身份的定向采集。
4. 人工标注所有标题 trial 的主题、长度、单行、无泄漏；业务 trial 按实际输出功能验证，特别检查 case 2 getter、case 26 API、case 28 JSON 信息完整性。按 source prefix 做训练/验证分离，不能用一个标题的不同 probe 点同时充当独立 holdout。

试答语义必须先可见，否则“将长度改为 10”只能得到快慢，不能解释误停/漏停的原因。

### 8.2 分两级选择，避免笛卡尔积扫描

**仅超参、现实现即可执行**：固定 T850/stride500/N5/min1/budget20000，对标题子集比较 `--fixed-prob-th 0.93 / 0.90 / 0.80`，逐输入 6 次 V/D 交替配对。业务集先保留 .93，并保留 `.85` 在 case 26 的负例用于校准，不直接生产应用。

标题识别来自明确的输入请求任务，不是模型输出关键词或线下 case ID。离线先用显式输入集合；若将来在线分场景用不同参数，可由实验代理对明确标题 wrapper 注入现有 fixed 参数，再讨论生产 scene 路由。当前 scene router 会将这些标题的内嵌业务内容分到 retrieval/code_generation 等，**没有已验收的 title scene**，本文件不虚构配置开关。

**需算法实验版本**：固定前缀先比较“原 cue/统一 final cue”和 trial 20/10；取得逐 token 数据后在同一 trial 的 prefix 上离线重算多个评分算法，再只将优胜的 1–2 个候选进入在线 paired replay。对 10-token 首检不确定者，测试同 child 延长，不做 10→20→50 三次独立 prefill。

正式性能以 off 测量；phase/raw 诊断单列。每个候选报告：

- 标题 E2E、完整 Agent task wall（补齐 start/end）、变快次数、P50/P95；标题收益计入，不因辅助身份删除。
- 每请求实际介入率、probe 次数/接受位置、永久隐藏 token、晋升 token、prefill/decode、候选丢弃量与 final 重启次数。
- 合格输出上的过早停止与不必要继续思考，不能只统计接受率；标题质量采用语义合格，不用字面等同 Vanilla。
- 控制器净收益：减少的原生思考成本，减去 probe、重复 prefill、CPU/队列等；完整任务质量仍独立验收。

### 8.3 最终推荐顺序

**近期：标题 `.90` 与 `.80` 有界回放 + trial 原文取证；随后比较 trial20/10 与统一 final cue。** 本轮 `.90` 是温和候选，`.80` 是探索性候选，不是默认上线值。

**中期：验证可晋升 trial，和拒绝后自然 boundary 同 child 续写。** 这两项分别减少接受、拒绝分支的重复提交，优先于仅优化几个毫秒的置信度 CPU 运算。

不建议现在就全局开启 Value-Min、把阈值大幅降低，或用英文“Final/Done”字符串作为硬停止条件。可见思考中的自述并非可靠就绪协议，代码中也可能引用这些文本；新增线上语义检查本身必须进入成本账本，且不能损害短请求旁路。
