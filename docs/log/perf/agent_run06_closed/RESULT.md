## 1. 结论

**按用户最新指定口径，只看按任务聚合的 LLM E2E 合计：两侧 DT 全通过子集已观察到省时，但全量、DTB 非劣、两侧全优和两侧全合格集合尚无总体时延收益。**不再以 session 活动跨度裁决本轮收益。

1. **实测：发现 1 个坏工具调用请求，但不是此前 close 接受后 fresh-final 的故障路径。**case29 子 agent 在原生旁路中生成到 32,000-token 上限，第 8 个 `write` 参数为空；无 abort/probe。Agent 收到 schema 错误后补写，最终报告 8/8 测试通过。10 个实际介入请求没有发现同类坏工具调用、非法工具名或标题边界泄漏。

## 6. 时延：按任务聚合 LLM E2E，再按质量筛选

### 6.1 指标与质量门定义

对 variant `x` 的任务 `i`：`L(x,i) = Σ metrics.e2e_ms / 1000`。先确定质量集合 `S`，再计算：

- **主指标：累计省时率** `100% × [1 − Σ L(D,i) / Σ L(V,i)]`，正数更快；对应节省秒数为 `ΣL(V,i) − ΣL(D,i)`。
- **辅助指标：任务等权省时率** `mean(100% × [1 − L(D,i)/L(V,i)])`，防止大任务掩盖小任务表现；另报更快任务数。
- 不按请求数取平均来替代任务总耗时，不按“哪些任务更快”挑选集合。请求数改变本来就是完整执行轨迹成本的一部分。

质量条件只使用质量证据，与耗时独立：

1. **DTB 非劣**：正式报告可比，按“编译阶段优先、编译成功后比较 DT 通过率”的观测结果不下降。两侧编译失败只算粗粒度持平，不是任务成功。本轮成员恰与报告评级顺序 `不合格 < 合格 < 良好 < 优秀` 的非劣集合相同；这不是一般等价关系，也不是有置信区间/容忍界的统计非劣检验。
2. **两侧全优**：两侧报告均评级“优秀”。不等于 DT 100%：case3 Vanilla 为14/15，仍被评级优秀。
3. **两侧全合格**：两侧报告评级均≥“合格”（含良好、优秀），不是只选恰为“合格”。不自行映射为某个 DT 通过率阈值：case37 Vanilla 实测1/3，但报告判为合格。该条件允许优秀→良好的退化，故再单列“合格且非劣”。
4. **两侧 DT 全通过**：两侧编译成功、已执行 DT 全部通过，没有失败/错误/跳过；正式报告主口径只含case28、34。仍受测试覆盖、主 agent 修补及测试执行一致性限制，不等于完整需求得到独立证明。
5. **case35 缺失处理**：Vanilla 无正式报告，不填造评级，不进入正式报告质量集合。原始36/36证据只进入单独的敏感性分析；其无SSE请求仍保留已记录E2E，不能当成正常协议样本。

- **非劣集合不等于同等工作量。**case2、3、29质量改善但合计多耗357.408秒；case26两侧失败仍多耗37.056秒。case28、34、37共省57.172秒，不能抵消上述增长，故正式非劣集合净多耗337.291秒。不能把这全部解释成控制器开销：编译后流程、修补、输出长度和采样轨迹也不同。
- **两侧合格接近持平不能替代非劣。**该集合包含case36，单例省161.758秒但4/4退为3/4；剔除这一质量退化后即变慢11.68%。
- **全优集合的拖累来自case3。**虽然两侧都“优秀”，14/15→15/15伴随多耗93.790秒，超过case28、34合计节省的22.314秒。因此“同评级”不等于“相同测试结果”。

### 6.4 正收益是否仅来自标题，如何用于后续验收

标题属于任务请求成本，按用户要求完整计入，不作为无效收益剔除。辅助拆分可帮助判断收益范围：

| 两侧DT全通过集合 | 标题 V→D 秒 | 标题省秒 | 业务主/子 agent V→D 秒 | 业务省秒 | 总省秒 |
| --- | --- | ---: | --- | ---: | ---: |
| case28、34 | 45.215→30.121 | 15.094 | 524.121→516.901 | 7.220 | 22.314 |
| 再加case35原始证据 | 84.224→46.508 | 37.716 | 990.912→954.468 | 36.444 | 74.160 |

这两个集合的业务合计也分别变快约1.38%、3.68%，故正收益不完全来自标题；但业务不是固定轮次同输入配对，仍不能据单轮差值归因给DTB算法。相反，全9任务业务合计仍变慢8.54%（第7节），不能把小子集的业务表现推广到全部场景。

建议固定输出三层结果：**全9任务总账**（不能隐藏质量退化）→**DTB非劣子集**（观察质量不降时的成本变化）→**两侧DT全通过子集**（当前最清晰的质量门后省时证据）。全优、全合格只作敏感性分析，不能取代真实DT结果。未来实验固定这套筛选规则，样本成员由各轮质量结果决定，并始终列明集合变化；本轮筛出的2/3例是事后条件分析，不是已证明普遍有效的场景路由规则。

协议门与任务质量门独立：case29最终8/8但有一次空参数write；不得因“非劣”隐藏该缺陷或从任务内扣除重试耗时。case35缺报告/无SSE也必须随敏感性结果披露。当前的“非劣”仅指观测测试结果，不能扩展为所有系统维度都非劣。

**当前可说：在两侧DT全通过的任务上，本轮close+.90已观测到累计LLM E2E优化3.92%，纳入原始测试证据为6.90%。当前不可说：该组合对全部9任务或全部非劣任务已实现稳定净省时。**每case各一次、未固定完整采样/部署身份，尚无统计显著性或稳定性保证。

### 7.2 本轮 probe 已不是主要总成本

10 次介入：8 个标题、case26 子 agent、case37 主 agent；12 次 probe，10 次接受，8 次首轮接受。标题中的 case34、37 各拒绝一轮并继续 500 token，其余直接接受。最终全部10个介入请求均经 confidence_accepted 进入 final。

probe 总量仅 **191 token / 17.449 秒**，其中 prefill **10.144 秒**、decode **6.415 秒**；占全部 LLM E2E **0.58%**。只有两次业务试答打满 50，其余 10 次自然 stop。相较旧 DTB run-06 的 897 token / 51.142 秒，probe 成本明显下降，但跨 run 请求轨迹不同，不将差值当成固定输入因果收益。

本轮 .90 相对 .93 的实际额外接受点只有 case37 主 agent 的 `.904024`；其余接受分数均≥.93，两个拒绝分数 `.858209/.887874` 均低于 .90。不存在“所有请求都因为降低阈值而更激进”的情况。

## 8. 下一步判断

1. **保留 close+.90 作为候选，不继续扩大参数扫描。**标题已呈现9对同输入的正收益，probe总成本只有0.58%；继续压 trial 即使有收益，也无法单独填平当前任务时延差距。
2. **优先收口两类独立问题。**可用性：把case29的“原生length+未完成tool+外层tool_calls”作为可恢复但真实的协议缺陷样例；质量：case26未知API与case36测试字符串/评测修补规则分别核对，不能靠阈值调低解决。
3. **下一轮固定上述LLM E2E与质量门口径。**保留全9任务总账和逐任务差值，按预先约定的非劣/全通过规则展示子集；标题、重试全计入，不再以session跨度裁决。记录编译失败是否提前退出、主agent修补代码/测试和测试执行范围；正式phase-off多次交替运行并匹配部署/采样/cache配置，检查质量门后收益能否稳定复现。
4. **在请求层关注长正文和多文件工具输出。**若可控制评测执行规范，验证按文件分批写入/局部edit能否减少整文件重写与单轮32,000截断；这是与DTB压思考不同的变量，应独立实验。此处仅提出方向，没有修改黑盒Agent或调用参数。
5. **历史fresh-final缺陷仍保留待取证。**本轮实际介入10次未复现坏工具，并不等于此前close回放缺陷已修复；可用现有定向stream_audit单独复现，不将诊断高频日志混入正式时延基线。
