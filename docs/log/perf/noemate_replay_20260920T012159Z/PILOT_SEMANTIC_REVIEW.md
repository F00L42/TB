# 六个试点的 Vanilla：前 750 token 是否足以转入回答

分析日期：2026-09-21。结论类型：对已采集输出的人工语义审阅；不是截断回放、参考答案评分或质量不退化证明。

## 1. 结论与口径

**这些样例支持把 750 作为直接答案策略的实验起点，但不支持“750 后均是无用思考”。** 告警分类、日志时间窗与排查方案在前 750 token 已有核心结论或完整提纲；告警清单仍在枚举，有覆盖遗漏风险；算术样例存在真实纠错，其中一次恰在 750 边界尚未显式写出正确平均值；知识库缺失样例则在 750 前已自然结束，不能算成 750 的压缩成功样例。

本次“试点”指已执行的 `noemate_replay_20260920T010816Z/pilot_h512` **6 个案例 × 2 次 Vanilla = 12 条输出**，不是计划中的 32 条校准集，也没有混入完整池中同案例的另一次回放。`pilot_h512` 是该实验目录名称，所审阅的 12 条均为 `variant=vanilla`，没有 H512 限制。

使用本地 Qwen3.6-27B tokenizer、`add_special_tokens=false` 对原始 reasoning 重编码，分别阅读 1–512、513–750 与 751 以后全部文本，并核对输入里的原始用户内容/工具结果和最终答案。计数不含 prompt 或最终正文，未取得服务器 token ID，因此是本地可见文本坐标。第 750 个 token 可以处于词或数值中间；这不是语义段落边界。

这里区分两件事：

- **证据与决策是否足够**：核心数据、计算结果或行动提纲已经形成，可以开始生成回答。
- **答案是否已在 reasoning 中完整写过**：不要求如此。DTB 的 final 仍保留完整原始 prompt、工具结果和思考前缀，可以组织措辞、继续计算或读取源材料；它不会只看到前 750 token 的 reasoning。

因此，后半段还有新条目不自动等于“不能早退”，后半段多次写“准备输出”也不自动等于“全部无用”。对运维建议仅判断相对输入的证据充分性，没有验证厂商命令、协议知识或现场根因。

### 试点 1：资料有了，但不能把后半段全部当成重复

问题是“CSCF网元有哪些典型的链路类告警？”。请求末尾已经有 5 条检索结果，包含紧急告警清单、IP 染色相关链路故障清单及对端域名不可达说明。模型从开头就决定基于检索结果总结。

两次在 750 处分别停在 `ALM-10224 ...链路` 和 `ALM-1` 的枚举中间。第一遍直到 1053–1060 才列到 `ALM-10871`，1158 起明确组织分类；第二遍对应位置为 1387–1394 和 1557。后段既有复制枚举和重复确认，也有尚未列出的类别，不能全部标成冗余。

但用户问的是“典型”，并非要求穷举 Vanilla 中每个 ID。完整原始检索仍交给 final，750 前也已有足够代表性材料。合理的早退目标是：给出有来源的典型分类和例子，避免只复述最先枚举的 P/I-CSCF、遗漏其他主要类型，或把半截 ID 拼错。不能以输出字数减少或未复刻 Vanilla 全表作为质量退化的唯一依据。

证据：[两次完整思考及最终输出](pilot_semantic_evidence/pilot_1.md)。

### 试点 2：分类结果已完成，后段主要是呈现

输入 user 消息 32、34……54 逐条提供了 ALM-2001～2012 的级别、时间与网元。两次前缀均完成：严重 2001/2004/2007/2010，重要 2002/2005/2008/2011，次要 2003/2006/2009/2012。第一次最后一组在第 467 token 结束，第二次在第 664 token 结束。

750 后分别只剩 105、95 token，内容是表头、简要建议与“数据是否完整”的重复确认，没有改变分组。**对核心分类任务，750 足以转入回答的证据较强。** 512 则没有同等证据：第二次直到 513 以后才完成最后一条抄录与实际分组。

最终答案附带的运维建议不是证明分类正确的必要条件，也未在本轮核验。重点检查 12 条是否完整、四条一组是否保持、字段是否与用户原文对应。

证据：[分类前缀和最终表格](pilot_semantic_evidence/pilot_2.md)。

### 试点 3：纠错是真工作，750 在临界处

工具原文提供 `92.641、88.315、71.253、85.792` 四个百分数。用十进制算术复核：总和 **338.001**，四点等权平均 **84.50025**。这只核对所给数据的算术，不把这些点的平均解释成按呼叫量加权的全天应答率。

| 事件 | 第一次 token 坐标 | 第二次 token 坐标 |
| --- | ---: | ---: |
| 先写出错误总和 337.999 | 252–258 | 252–258 |
| 先写出错误平均值 84.49975 | 276–283 | 276–283 |
| 首次出现正确总和 338.001 | 655–661 | 615–621 |
| 首次出现正确平均值 84.50025 | 678–685 | **751–758** |

第一次到 750 时已经有正确结果，后面继续做竖式复核。第二次到 750 时，文本恰好停在 `Average = 338.001 / 4 = `，正确平均值紧接着才写出。**这说明 512–750 之间存在重要纠错，不能简单推到 512；也说明不能声称两次在 750 前都已完成数值结论。**

但正确分子和除数已在第二次前缀中，final 可以完成除法，因此“正确数值首次出现在 751”不能证明 direct750 必然错误。该样例应成为下一轮重点核查项：是否返回 338.001 / 84.50025，是否混用早先错误值，而不是只看接口正常。

另有独立的输入范围问题：用户问“今日”，工具返回日期为 **2026-07-30**，而工具状态起始时间是 **2026-09-18**。第一次最终正文标注了数据日期但仍称“今日总和”，第二次未标注日期。延长 thinking 并未消除该问题；压缩后的答案至少不能把旧日期数据无条件当成今日数据。这是原始数据与表述的一致性问题，不归因于 DTB。

证据：[数值样例完整分段](pilot_semantic_evidence/pilot_3.md)、[精确坐标与 Decimal 复核](pilot_semantic_evidence/landmarks.json)。

### 试点 4：无知识不能靠继续思考补足

请求已经有三次 Rag `NO_INDEX`。两次 Vanilla 在 681/667 token 自然结束，均回复“当前知识库无法提供足够信息回答此问题”。中间反复在自行猜测原因值和遵守 Skill 的拒绝猜测约束之间摇摆，后段没有新增检索证据。

H750 在这两次轨迹中不会触发，所以不能作为 direct750 有效压缩的证明。语义上可以更早决定报告证据不足，但这不等于已经回答原因值含义。历史记录期望再次调用 Rag，因此脚本标了 `expected_tool_call_missing`；这里仍保留异常，不把“拒答合理”擅自升级为业务正确性通过。

证据：[自然结束与最终受限回答](pilot_semantic_evidence/pilot_4.md)。

### 试点 5：关键时间推导很早完成，后段主要写草稿

用户给出故障发生时刻 21:58:32，记忆给出“故障明确时收集此前两小时操作日志”。两次分别在 196–213、197–214 token 写出 **19:58:32～21:58:32**；随后已有操作、运行、告警或信令日志的规划。到 750 时关键信息和回答结构已具备。

第一遍后面 252 token 主要重述结构与检查偏好；第二遍后面 522 token 继续写告警/信令细节和输出要求。它们并非每句都重复，但多数是可放到 final 中完成的成文工作，没有新增工具证据。

第二次最终答案以 `length` 截断，说明重复起草可能挤占外部 completion 额度。direct750 有机会给 final 留出更多额度，但是否真的避免截断须看新输出。核心时间窗可作为确定检查项；厂商命令、协议描述和根因判断未验证，不能直接把 Vanilla 全文当金标准。

证据：[日志分析方案与第二次截断](pilot_semantic_evidence/pilot_5.md)。

### 试点 6：可以生成排查步骤，不等于已经定位根因

前缀已归纳用户提供的时间、CPU >85%、N2 重传和语音失败率变化，并在第 294 / 321 token 前形成五步提纲。到 750 时两次分别已展开到步骤3、步骤4。后段继续完成日志确认、配置变更核对、恢复验证、维护窗口和双人复核等内容。

因此前 750 足以支持开始输出**排查计划**，但还不能把后面的分支和约束全部删除。尤其第二次后段出现“负载回落后告警将自动清除”等强断言，没有新增工具观测支持；更长思考也不等于因果证据更充分。下一轮应保留“先采集/核查，再确认或排除”的关系，不能因为更短就把待验证的过载假设变成确定结论。

证据：[两个不同提纲及完整正文](pilot_semantic_evidence/pilot_6.md)。

## 3. 对下一轮实验的影响

仍建议先运行现有 direct750 对照，而不立即把介入值降到 512。新增语义证据支持这一选择：告警分类第二次到 664 才完成分组，数值样例两次都在 512 后发生关键纠错。750 也不是绝对安全边界，数值第二次紧贴边界，列表/方案的完整性依赖 final 继续组织原始材料。

第 6 节 32 条集合已经包含这六例，无需改动采样或同时改超参。对新 direct750 输出额外保留以下轻量语义核对记录，不引入服务器参考答案测试集或全量 Judge：

1. pool line 399：求和/平均是否正确；数据日期是否说明；区分错数值与合理舍入。
2. line 178：12 条告警三组映射是否完整，无重复/遗漏/错组。
3. line 131：前两小时的操作日志窗是否保留，最终正文是否完整结束。
4. line 130：是否保留排查与验证步骤，假设是否被误写为已确认根因。
5. line 319：典型类别是否有代表性，ID/名称是否对应原检索，允许合理精简枚举。
6. line 386：是否仍自然结束并说明知识不足，历史工具动作偏离继续单列。

这里的语义审阅增强了“值得测试”的理由，不构成“正确率不下降”的验收。不要把 Vanilla 750 前缀拼上 Vanilla 原答案当成 direct750 结果；只有服务器实际施加 cue 后生成的回答才是待测输出。
