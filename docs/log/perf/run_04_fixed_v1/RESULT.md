# run_04_fixed_v1：固定参数实验结果与下一轮计划

## 0. 结论

`run_04_fixed_v1` 使用 `docs/debug/fixed_param` 中每个测试集的 `fixed_v1` 参数。本轮
633/633 个请求均进入 `fixed` 分支，生效配置和参数文件一致，无客户端错误。

相对 run_04 Vanilla：

- 13/13 个测试集的平均 E2E 均有正收益；
- 场景等权宏平均 paired E2E gain 为 **97.3261 s / 49.47%**；
- 请求加权平均 E2E 从 170.6025 s 降至 89.2205 s，改善
  **81.3820 s / 47.70%**；
- 607/633（95.89%）个配对请求更快；
- completion token 加权平均减少 1878.01，降幅 60.06%。

相对 run_04 `dtb_default`：

- 12/13 个测试集平均更快；
- 请求加权平均改善 **91.5206 s / 50.64%**；
- 606/633 个配对请求更快；
- completion token 加权平均减少 1614.12，降幅 56.38%；
- 唯一更慢的“ReAct 白盒整体规划”只回退 2.36 s，但正确条目由 8 提升到 13。

因此 fixed 场景定制方向成立，下一轮不应回到当前 `dtb_default` 动态预算。当前
`fixed_v1` 仍不能作为最终策略：虽然 13 场景宏平均 Judge 正确率比 Vanilla 高
0.13 个百分点，但 8 个具体测试集的正确条目下降，不满足“每场景质量非劣”的严格
硬门。

## 1. 目的、输入与口径

目的：在质量门约束下最大化产品测试集端到端时延收益，并确定下一轮每个测试集应该
继续压缩还是回补思考。

输入：

- 基线：[`../run_04/test_result`](../run_04/test_result) 中 13 个 Vanilla 和 13 个
  `dtb_default`；
- 候选：[`test_result`](test_result) 中 13 个 `fixed_v1`；
- 裁决与 phase：[`extracted`](extracted) 下请求级 `requests.jsonl` 和
  `controller_phases.jsonl`；
- fixed 参数：[`../../../debug/fixed_param`](../../../debug/fixed_param)。

以测试集名称去 variant 前缀和时间戳后缀后配对，再以 `QA_ID` 做请求级等值关联：

```text
paired_gain_i = E2E_vanilla_i - E2E_fixed_i
default_gain_i = E2E_dtb_default_i - E2E_fixed_i
```

13 个测试集均完整配对，共 633 对；没有只存在于某一 variant 的 `QA_ID`。平均收益
百分比使用 `mean(paired_gain) / mean(baseline E2E)`。宏平均对 13 个测试集等权，请求
加权平均对 633 个请求等权。

### 5.1 总模型工作量

| visible think token | 2683.90 | 990.70 | -63.09% |
| hidden probe token | 43.44 | 92.03 | +111.82% |

| generate calls | 11.36 | 6.41 | -43.55% |
| accounted phase wall | 180.64 s | 89.13 s | -50.66% |

fixed_v1 的主要收益来自大幅减少可见思考和 generate call；即使隐藏 probe 翻倍，总
模型工作量仍下降 54.17%。下一轮应关注 probe 频率：预算受限场景连续试探较多，增大
stride 可能在回补思考的同时减少 probe/prefill 次数。

## 6. 下一轮实验：fixed_v2

### 6.1 设计原则

下一轮仍只为每个测试集运行一个候选，避免组合爆炸：

1. **质量已通过、预算受限**：把总预算由约 `0.50*T50` 压到 `0.35*T50`；
2. **质量已通过、首次停止**：总预算不变，只把首次检查由约 `0.20*T50` 压到
   `0.15*T50`；
3. **质量下降、预算受限**：总预算提高到约 `0.65*T50`，并增大 stride 以减少反复
   probe；
4. **质量下降、首次停止**：首次检查提高到约 `0.30*T50`，总预算提高到
   `0.65*T50`；
5. **规划模块混合形态**：保持首次检查，预算提高到 `0.65*T50`，阈值提高到 0.95。

这里的 `T50` 沿用 fixed_v1 的同一 Vanilla 思考长度估计；所有值继续按 50 token
取整。`fixed_num_thinking` 由预算、check 和 stride 重新推导。

### 6.3 执行顺序

1. 先运行 8 个质量回补候选；任何场景仍低于 Vanilla 时，只继续该场景局部搜索；
2. 再运行 5 个继续压缩候选；若质量下降则直接保留 fixed_v1，不追加更激进点；
3. 组合每个场景已通过质量门且 paired E2E gain 最大的候选，形成首个 13 场景
   best-observed 组合；
4. 只有组合通过场景质量门和宏平均门后，才开始合并相近 profile 和自动 scene 路由。

## 7. fixed_v2 验收标准

- [ ] 与 Vanilla、DTB default、fixed_v1 的 `QA_ID` 完整配对；
- [ ] 633/633 请求进入 `fixed`，生效值和候选文件一致；
- [ ] 不新增客户端错误或 hard failure；
- [ ] 未预先声明非零 margin 时，每个测试集正确条目不少于 Vanilla；
- [ ] 质量通过后按该测试集 `mean(E2E_vanilla - E2E_candidate)` 最大选择；
- [ ] 收益场景同时报告负收益请求比例、visible/hidden/final token 和 phase wall；
- [ ] 组合策略的 13 场景宏平均 paired gain 为正，且质量宏平均非劣；
- [ ] Judge 不进入被测请求 E2E 或 DTB phase 汇总。

## 8. 证据边界

- E2E、completion token、Judge、分支和 phase 数值为 **实测**；
- 停止形态与下一候选方向是从 telemetry 得出的 **实验假设**，必须由 fixed_v2 证伪或
  证实；
- 当前没有正式声明的统计非劣 margin，因此不能仅凭宏平均略升宣布 fixed_v1 质量
  通过；
- 本轮没有客户端错误，但 Judge 错误不等同于已完成人工 hard-failure 审核。
