# run_05_fixed_v2 实验结果与下一轮决策

## 0. 结论

`fixed_v2` 相比 Vanilla 仍保持显著收益，但不能作为 13 场景统一最终策略：

- **实测**：13/13 个测试集的平均 E2E 均快于 Vanilla；633 请求加权平均由
  170.6025 s 降至 91.8638 s，改善 **78.7387 s / 46.15%**；场景等权宏平均
  paired gain 为 **96.0345 s / 49.71%**。
- **实测**：相比 fixed_v1，加权平均 E2E 回退 2.6433 s / 2.96%。这是 v2 有意对
  8 个质量回补场景增加思考的结果；5 个继续压缩场景全部比 v1 更快。
- **实测**：v2 微平均正确数为 558/633，与 Vanilla 相同，比 fixed_v1 多 5 条；
  场景等权宏平均正确率比 Vanilla 高 0.32 pp。但只有 6/13 个场景逐场景非劣，仍未
  通过严格质量门。
- **决策**：不再做完整 13 场景 fixed 搜索。冻结 6 个 v2 候选，2 个场景回退到
  已通过质量门的 v1；只对余下 5 个质量未过门场景继续 fixed_v3，并为 2 个回退场景
  各测一个中点候选。
- **决策**：现在可以开始离线预算聚类、分类函数和候选配置调试；但不能把自动路由
  配置视为最终结果。自动回放必须等待未命中/未解决场景能够明确 native bypass，且
  预算字段来源从 `fixed_*` 切换为 `scene` 后再验收。

## 1. 输入、配对与生效审计

比较输入：

- Vanilla：[`run_04`](../run_04) 中 13 个 `vanilla_*.csv`；
- fixed_v1：[`run_04_fixed_v1`](../run_04_fixed_v1)；
- fixed_v2：本目录 `test_result/` 和 `extracted/`。

三轮均按“规范化测试集名 + `QA_ID`”严格配对，共 13 个测试集、633 对请求。E2E
收益定义为 `baseline E2E - candidate E2E`，正数表示 candidate 更快；百分比使用
`mean(paired gain) / mean(baseline E2E)`。宏平均对测试集等权，请求加权平均对
633 个请求等权。

fixed_v2 的提取与裁决审计闭合：

| 审计项 | 结果 |
| --- | ---: |
| 结果 CSV / 客户端请求 | 13 / 633 |
| 日志中 phase / 被选择 phase / 排除 phase | 4286 / 4286 / 0 |
| 有 `requests.jsonl` 的请求 | 633/633 |
| `decision_branch=fixed` | 633/633 |
| 客户端错误 | 0 |

每个测试集只有一组生效配置，`check_length`、`min_think_budget`、`num_thinking`、
`think_stride` 和 confidence 的来源均为对应 `fixed_*` 字段；hard limit 的来源记录为
`context/request/config`，其值等于 `fixed_budget_tokens`。所有值均与
[`docs/debug/fixed_param`](../../../debug/fixed_param) 中 v2 段一致。fixed 分支优先于
scene、difficulty 和 history，因此本轮记录的 scene 结果没有改变实际预算。

## 4. best-observed 组合

在当前 search 数据上，按“先通过 Vanilla 逐场景正确数门，再选 E2E 最快”可组成：

- 使用 v2：整体规划、机器数据分析、KPI、NetQAD 单步规划、NetQAD 规划模块、
  长文本根因，共 6 个测试集；
- 使用 v1：告警诊断建议总结、投诉分类中文，共 2 个测试集；
- 暂时使用 Vanilla/native：白盒单步规划、事件自闭环、告警诊断结论总结、投诉助理
  工具调用、投诉分类英文，共 5 个测试集。

这个组合在 search 数据上的场景宏平均 gain 为 60.0473 s / 29.62%，请求加权平均
gain 为 54.1600 s / 31.75%；正确数为 572/633，13 个场景均不低于各自 Vanilla。
它证明“已通过场景先自动优化、其余场景拒识回原生”在收益上可行，但这是在同一数据
上选点后的 **best observed**，不能替代新 holdout 验证。

## 5. telemetry 解释

### 5.1 总模型工作量

| 请求级均值 | fixed_v1 | fixed_v2 | v2 相比 v1 |
| --- | ---: | ---: | ---: |
| visible think token | 990.70 | 1095.81 | +10.61% |
| hidden probe token | 92.03 | 83.28 | -9.50% |
| final answer token | 258.22 | 234.69 | -9.11% |
| 总模型生成 token | 1340.95 | 1413.79 | +5.43% |
| generate calls | 6.41 | 5.77 | -10.00% |
| probe rounds | 2.52 | 2.19 | -13.23% |
| accounted phase wall | 89.13 s | 91.77 s | +2.96% |

v2 增加了总思考量，但更大的 stride 和更晚的首次检查减少了 probe 和 generate call，
所以 E2E 回退小于可见思考增幅。下一轮质量回补仍优先增加一次有效思考长度，而不是
增加大量小 stride probe。

### 5.2 剩余质量缺口的停止形态

- 白盒单步规划：平均使用预算 82.0%，21/79 请求耗尽预算；4 个 V-only 样本中 3 个
  已到最后一轮或预算上限。继续提高总预算比只调 confidence 更有针对性。
- 事件自闭环：24/25 在首次 probe 停止；V-only 样本 confidence 为 0.9842 和
  0.9861。提高阈值到 0.95 无效，应提高首次检查长度。
- 告警结论总结：13/13 首次停止，唯一 V-only 样本 confidence 为 0.9721；应继续
  提高首次检查长度。
- 投诉工具调用：39/39 首次停止，两个 V-only 样本 confidence 为 0.9795、0.9777；
  应继续提高首次检查长度。
- 投诉分类英文：唯一 V-only 样本在 400 token 首次停止，confidence 为 0.9532；
  虽然总体以预算受限为主，针对质量缺口仍应先提高首次检查长度。

这些 confidence 已经很高，因此继续统一上调 `fixed_prob_th` 既不能稳定捕获前三类
错误，又会给其他请求增加预算；v3 不采用全场景统一阈值实验。

## 6. 是否开始聚类和分类调试

### 6.1 可以立即开始的工作

可以开始，但限定为**离线候选工作**：

1. 以第 4 节的 8 个已通过场景建立 CandidatePolicy manifest；5 个未解决场景先标记
   `reject/native`，不为它们绑定 default DTB 预算。
2. 对通过质量门的预算向量做 exact/near clustering。聚类只是实验和配置生成步骤；
   运行时仍保持 `可见请求特征 → scene/reject → scene 预算`，不新增必经
   `BudgetProfile` dataclass。多个 scene 可以在 YAML 中复制同一预算。
3. 从 13 个结果 CSV 构造分类 search/holdout 与跨场景负例，扩展
   `tests/test_adapter_scene_classifier.py`。先验证 route/reject，再验证预算值。
4. 使用 fixed_v2 telemetry 作为当前分类器基线：`fault_diagnosis` 吞入 560/633 个
   请求，来自多个需要明显不同预算的测试集；另有 39 个 `general`、26 个
   `code_generation`、6 个 `planning`、2 个 `retrieval`。当前 coarse scene 不能直接
   承载 best-observed 预算。

### 6.2 暂时不能做的工作

- 不能把当前 8 个预算直接写成最终自动配置并宣布完成：当前 fixed 分支掩盖了 route
  误差，尚未实测 `decision_branch=scene` 和各字段来源为 `scene`。
- 未解决或 OOD 请求必须真正走 native bypass。若 reject 在 history 关闭时仍进入
  default 控制器状态机，应先修复/验证该分支，再运行自动 holdout；否则第 4 节组合的
  质量与时延推导不成立。
- 不能用本轮参与参数选择的 633 条请求同时声称自动策略泛化；产品自动模式至少需要
  新 holdout，之后再做一次开源/OOD 拒识测试。

因此，**分类与 fixed_v3 并行，最终配置收口等待 fixed_v3**，而不是二选一。

执行和选择规则：

1. 维持与 run_04/run_05 相同的样本、顺序、采样、并发、到达节奏和 cache 条件；
2. 先运行 5 个未过门场景；若仍低于 Vanilla，停止继续增加全量固定参数点，改为人工
   复核翻转样本，并让该 scene 在首个自动版本中 reject/native；
3. 中点候选只有在正确数不低于 Vanilla 且快于已选择 v1 时才晋级，否则保留 v1；
4. 参数选择完成后，聚类候选必须通过共享预算交叉回放，不能只按参数欧氏距离合并；
5. 自动模式用新 holdout 验收 route、reject、effective budget、逐场景质量和宏平均
   paired E2E gain。

## 8. 验收与证据边界

- [x] 13 个测试集、633 个 QA_ID 三方完整配对；
- [x] fixed_v2 的 633 个请求全部命中 fixed，配置和值来源闭合；

- [ ] fixed_v2 仅 6/13 场景通过严格逐场景质量门；
- [ ] best-observed 组合仍需新产品 holdout，不能把 search 选择结果当泛化结论；
- [ ] 自动路由需证明 reject/native、scene 分类和预算来源均正确；
- [ ] hard failure 目前只有客户端 `错误` 字段可审计；语义 hard failure 尚未独立标注。

证伪。
