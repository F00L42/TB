# run_07_vanilla：Vanilla 重复性与 run_07 质量基线敏感性分析

## 0. 结论

本轮是 13 个产品问题集的原生单次生成重复实验，完全没有启用 Think Budget。客户端
CSV 已足够完成 E2E、Token 和质量分析；没有 `server.log`、TB telemetry 或提取目录是
符合实验边界的，不需要补做 phase 提取。

- **实测——输入闭合**：run_04 Vanilla、run_07_vanilla 和 run_07 DTB 均为同一批
  13 个问题集、633 条请求；按“问题集 + `QA_ID`”配对后，问题和参考答案 633/633
  完全一致，没有客户端错误。
- **实测——Vanilla 质量存在明显轮间波动**：run_04 为 558/633，本轮为
  567/633，增加 9 题；但逐题不是单向改善，而是 13 题只在 run_04 正确、22 题只在
  本轮正确，共 35/633 条发生正确性翻转。
- **实测——本轮 Vanilla 性能状态明显更慢**：平均 E2E 从 170.6025 s 增至
  220.0387 s，增加 49.4362 s / 28.98%，13/13 问题集平均值、P50 和 P95 均变慢；
  completion token 仅增加 0.74%。这更像服务吞吐/运行状态差异，而不是输出长度变化，
  但缺少 manifest，原因保持未归因。
- **实测——不能通过逐问题集选基线得到“13/13 都没有多错”**：即使每个问题集都
  选择两轮 Vanilla 中正确数较低的一轮，run_07 DTB 仍在 NetQAD 规划模块、事件
  自闭环、告警建议总结、告警结论总结、投诉分类英文 5 个问题集各少 1 题。
- **实测——可以得到更有利但必须标注为事后敏感性分析的口径**：逐问题集取较低
  Vanilla 正确数后，组合基线为 556/633，run_07 DTB 为 558/633，即微平均多 2 题；
  8/13 问题集严格非劣，另 5/13 各少 1 题，13/13 通过当前一题容差门。

因此，“run_07 没有比 Vanilla 多错”只有两种有限且真实的含义：

1. 相对预先使用的 run_04 Vanilla，**全量微平均**同为 558/633；
2. 相对两轮 Vanilla 的逐问题集低值组合，**全量微平均**为 558 对 556。

它不能表述成“run_07 在每个问题集都不低于 Vanilla”。逐问题集事后挑较低基线属于
baseline-floor 敏感性分析，不应替换正式主基线。

## 1. 输入与证据边界

权威输入：

- 本轮重复 Vanilla：[`test_result/_SUMMARY.csv`](test_result/_SUMMARY.csv) 及 13 个
  `vanilla_*.csv`；
- 原 Vanilla：[`run_04/test_result/_SUMMARY.csv`](../run_04/test_result/_SUMMARY.csv)
  中的 13 个 `vanilla_*.csv`；
- 自动 DTB：[`run_07/test_result/_SUMMARY.csv`](../run_07/test_result/_SUMMARY.csv)
  及对应明细；run_07 唯一无效 Judge `MAECOM00116` 沿用人工复核结果，按错误计。

完整性结果：

| 检查项 | 结果 |
| --- | ---: |
| 问题集 | 13 |
| 每个 variant 的客户端请求 | 633 |
| run_07_vanilla 非空且唯一 request_id | 633/633 |
| 各问题集 QA_ID 集合一致 | 13/13 |
| 同问题集、同 QA_ID 的问题和参考答案一致 | 633/633 |
| run_04 / run_07_vanilla 自动有效裁判 | 633 / 633 |
| run_07 自动有效 + 人工裁决 | 632 + 1 |
| 三侧客户端错误 | 0 / 0 / 0 |

`QA_ID` 会在不同问题集间复用，因此配对键必须是“规范化问题集名 + `QA_ID`”，不能只
使用全 run 的 `QA_ID`。两轮 Vanilla 的 Judge 方法计数均为 623 条 `llm_judge` 和
10 条 `deterministic_exact`；只有 2 条请求在两种 Judge 方法间互换。正确性翻转主要
反映两次模型回答和裁决结果的联合波动，不能仅归因为 Judge 方法变化。

本轮没有 `manifest.json`，不能确认两轮 Vanilla 及 run_07 DTB 的服务 commit、生成
sampling/seed、并发、到达节奏和 prefix cache 状态完全相同。本文只能报告已归档客户端
结果的**实测差异**；对 28.98% E2E 变化和正确性波动的原因不作推断。

## 2. 两轮 Vanilla 总体比较

| 指标 | run_04 Vanilla | run_07_vanilla | 本轮−run_04 |
| --- | ---: | ---: | ---: |
| 总 E2E | 107,991.3928 s | 139,284.5054 s | +31,293.1126 s |
| 请求加权平均 E2E | 170.6025 s | 220.0387 s | +49.4362 s / +28.98% |
| completion token | 1,979,309 | 1,993,930 | +14,621 / +0.74% |
| 平均 completion token | 3,126.87 | 3,149.97 | +23.10 |
| 正确数 | 558/633 | 567/633 | +9 |
| 请求加权正确率 | 88.15% | 89.57% | +1.42 pp |
| 问题集等权正确率 | 86.94% | 90.34% | +3.40 pp |

本轮 13/13 问题集的平均 E2E 都更慢，增幅为 16.90%～34.65%；13/13 的 P50 和 P95
也都更慢，其中 P50 增幅为 20.73%～47.88%，P95 增幅为 9.48%～38.52%。与此同时，
各问题集平均 completion token 的变化只有 -5.62%～+3.97%。因此新 Vanilla 可以作为
“另一轮基线观察”，但不能在缺少 manifest 时直接取代 run_04 并把更大的时延差归因给
DTB。

`04-only / 07V-only` 表示该问题集中只在对应一轮 Vanilla 判对的请求数。

| 事件自闭环 | 25 | 24 | 24 | 0 | 0 / 0 |

两次 Vanilla 的正确数差异并不等于只有 9 条不稳定：实际有 35 条发生方向相反的翻转。
白盒机器数据分析单问题集相差 4 题，告警建议总结和长文本根因推理各相差 2 题，说明
“一轮 Vanilla 正确数”不是稳定常数。后续若要收紧到严格逐问题集非劣，应让 Vanilla
和 DTB 都做相同次数重复，而不是只重复 Vanilla 后择低比较。

## 4. run_07 在三种基线口径下的结果

质量状态定义：

- 严格：`DTB_correct >= Vanilla_correct`；
- 少 1 题：`DTB_correct = Vanilla_correct - 1`；
- 失败：少 2 题及以上。

| 基线口径 | Vanilla 正确 | run_07 正确 | 微平均变化 | 严格 / 少1题 / 失败 | DTB 请求加权 E2E 收益 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 固定使用 run_04 | 558 | 558 | 0 / 0.00 pp | 7 / 6 / 0 | 44.58% |
| 固定使用 run_07_vanilla | 567 | 558 | -9 / -1.42 pp | 5 / 5 / 3 | 57.03% |
| 每问题集取较低 Vanilla 正确数 | 556 | 558 | +2 / +0.32 pp | 8 / 5 / 0 | 48.65% |

第三行的 E2E 只为展示这组混合基线会产生什么数值：请求加权基线为 184.1350 s，
run_07 为 94.5468 s，收益 89.5882 s / 48.65%；问题集等权相对收益为 53.05%。它把
两个不同运行状态下的问题集拼成一条虚拟基线，不能作为正式性能结论。正式性能仍应
分别相对完整的 run_04 或完整的 run_07_vanilla 报告。

质量的宏平均也没有随着微平均同步变好：低值组合的问题集等权正确率为 86.79%，
run_07 为 86.64%，仍低 0.16 pp。所谓“+2 题”只适用于 633 请求微平均总数。

## 5. 逐问题集的质量有利选择

选择规则为：两轮 Vanilla 中正确数较低者作为该问题集的 baseline floor；若两轮正确数
相同，为减少任意切换而保留 run_04。该规则是看到结果后的敏感性分析，不是预声明实验
设计。

若目标只是让质量表在不伪造数据的前提下更有利，可以使用以下组合：

- 使用 run_07_vanilla：NetQAD E2E 单步规划、投诉分类中文；
- 使用 run_04：其余 11 个问题集，其中 5 个只是两轮正确数相同而沿用原基线。

## 6. 建议采用的报告方式

### 6.1 正式主结论

继续保留 run_04 作为 run_07 已预先使用的主基线：

```text
run_07 与 run_04 Vanilla 微平均同为 558/633；
7 个问题集严格非劣，6 个问题集各少 1 题；
13/13 通过预声明的一题容差门；
请求加权 E2E 改善 44.58%。
```

本轮重复 Vanilla 作为稳定性补充，而不是在看到 run_07 后逐问题集替换主基线。

### 6.2 可以使用的敏感性表述

```text
两轮 Vanilla 的正确数为 558/633 和 567/633，35 条请求发生正确性翻转。
若按问题集取较低的已观测 Vanilla 正确数作为波动下沿，组合基线为 556/633，
run_07 为 558/633；8/13 问题集严格非劣，其余 5/13 各少 1 题。
```

这个表述能说明 run_07 的质量处于 Vanilla 重复波动附近，并完整披露选择规则；不能
简写为“13/13 精度不下降”。

### 6.3 下一次正式质量实验

1. 在执行前声明单一基线或聚合规则，不根据 DTB 正确数选择 Vanilla 轮次；
2. Vanilla 与 DTB 使用相同重复次数、sampling/seed、Judge 参数、服务状态和执行顺序；
3. 至少记录 manifest，并优先交错执行 `Vanilla → DTB`，减少长时间服务状态漂移；
4. 对重复结果报告每问题集的正确数区间、正确性翻转和 hard failure，而不是只保留最有利
   的一次；
5. 若仍沿用当前一题容差门，run_07 已经通过，无需为得到“严格 13/13”重新解释基线。

## 7. 证据强度与限制

- 本文的样本一致性、E2E、Token、Judge、正确数及请求级翻转均为**实测**。
- “原生 Vanilla 不需要 TB server.log/phase 提取”由实验请求边界和当前 telemetry 设计
  确定，属于**源码确定**。
- 对本轮 Vanilla 变慢及质量提高的具体原因没有 manifest 或服务端证据，保持**未归因**。
- 逐问题集低值组合是明确标注的**事后敏感性分析**，不是独立服务器 run，也不是新的
  实测运行环境。
