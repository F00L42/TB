# 算法一致性检视
## 背景
AGENTS.md
docs/design/budget_forcing_migration.md
## 目的
检视think_budget_vllm_adapter实现是否符合"覆盖所有算法实现，复用集成 vLLM 的接口"的原则。
### 边界
* 可以参考deer
  * 侵入式修改vllm的部分：参数注册、"绑架"_create_chat_completion方法的实现、流式透传实现
  * 状态设计模式：使用状态转换逻辑描述不同的提交阶段，以及这些阶段间的切换条件
    * 但不必要完整使用deer定义的所有状态，如果三个状态足够描述think_budget_vllm_adapter的算法逻辑，就没有必要使用四个
* 必须使用think_budget的实现覆盖，不可以沿用deer
  * 算法逻辑
    * 超参配置（至少统一沿用原来的参数配置逻辑，如TRIAL_ANSWER_LENGTH就应该收编重新赋值为50，对于判断可以收纳到配置文件中但目前写死在代码里的参数，可以先记录）
    * 分支行为
* 特例：置信度校验结果超过阈值时，deer的处理逻辑是依然丢弃_ConfidenceCheckState生成的trial answer，进入_AnswerState仅添加</think>生成最终答案，而think_budget的处理更加复杂，一些情况下可以直接使用校验过程中的答案
  * 性能分析发现，如果不限制trial answer的长度，会极大拖慢端到端时延（docs/log/perf/run_00/RESULT.md），因此限制为50token，那么大概率无法沿用trial answer
  * 所以这里决定先使用deer的实现逻辑，可以设计一个测试方案来实验是否存在更优的校验逻辑
* 如果在检视过程中发现其他模糊的实现，先和用户讨论，再下结论
## 建议
docs/debug中输出think_budget_vllm_adapter检视报告和重构方案，指出所有与迁移原则不符合的实现及整体重构计划，不动源码

## 需澄清的差异点
### F-02
* 总是使用clean-context 分支，从浅拷贝 child prompt 探测，失败 trial 不进入主上下文的做法没有问题，无需修改
* trial prompt中`is_code`的判断条件沿用自deer，这个判断可以丢弃，和think_budget的clean-context 分支行为统一
* 配置投影是问题，应该取消并和think_budget对齐
* "输出中 <think> / </think> 是否配对"能否简化？因为一条推理轨迹中总是只有一次<think></think>闭合

### F-04

逻辑应为：首先匹配识别任务类型，然后如果匹配上执行难度估计，难度估计与任务类型的budget进行平均，如果没匹配上进入历史估计（历史估计须存储，不进行再一次难度估计）

### F-05
参考commit ID `6f2de8c0`中新提交的think_budget_refactored_final实现更新历史数据

### F-06
判断迁移预算放大和回退行为可以丢弃，理由：不再涉及API调用，优先配合限制trial answer的长度为50token的逻辑

### F-07
</think>是否为结构 token不重要，因为根据vllm的stop推理参数它不会在trial answer中出现
其他均应该与参考保持一致

### F-09
soft truncation是为了用户阅读体验，但实际上这样的做法会导致128 token的KVcache block难以流畅生成，导致性能大幅下滑（比如5次重新提交都没有保存到KVcache，那么就多出了5个完整首字的端到端时延约10s），判断可以抛弃这个特性

### F-10
可以弃用answer_list，优先配合限制trial answer的长度为50token的逻辑

### F-11
可以保留statistics_aggregation分类

### F-12
1. 不需要加入ConfigDict(extra="forbid")
2. 不关注beam_search，判断可以丢弃
