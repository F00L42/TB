# 算法一致性检视
## 背景
AGENTS.md
docs/design/budget_forcing_migration.md
## 目的
检视think_budget_vllm_adapter实现是否符合"覆盖所有算法实现，复用集成 vLLM 的接口"的原则。
### 边界
* 可以参考deer
  * 侵入式修改vllm的部分：参数注册、"绑架"_create_chat_completion方法的实现、流式透传实现
  * 状态设计模式：使用状态转换逻辑描述不同的提交阶段，以及这些阶段间的切换条件
    * 但不必要完整使用deer定义的所有状态，如果三个状态足够描述think_budget_vllm_adapter的算法逻辑，就没有必要使用四个
* 必须使用think_budget的实现覆盖，不可以沿用deer
  * 算法逻辑
    * 超参配置（至少统一沿用原来的参数配置逻辑，如TRIAL_ANSWER_LENGTH就应该收编重新赋值为50，对于判断可以收纳到配置文件中但目前写死在代码里的参数，可以先记录）
    * 分支行为
* 特例：置信度校验结果超过阈值时，deer的处理逻辑是依然丢弃_ConfidenceCheckState生成的trial answer，进入_AnswerState仅添加</think>生成最终答案，而think_budget的处理更加复杂，一些情况下可以直接使用校验过程中的答案
  * 性能分析发现，如果不限制trial answer的长度，会极大拖慢端到端时延（docs/log/perf/run_00/RESULT.md），因此限制为50token，那么大概率无法沿用trial answer
  * 所以这里决定先使用deer的实现逻辑，可以设计一个测试方案来实验是否存在更优的校验逻辑
* 如果在检视过程中发现其他模糊的实现，先和用户讨论，再下结论
## 建议
docs/debug中输出think_budget_vllm_adapter检视报告和重构方案，指出所有与迁移原则不符合的实现及整体重构计划，不动源码
