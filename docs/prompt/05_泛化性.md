# think_budget_generalization_plan评审
记录澄清后的设计目的，列出具体重构和采集打点计划，用户接下来会提供服务器上13场景的
* vanilla基线
* 仅开启dtb
* 按照你给的基于vanilla构造的传入fixed_think_stride等定制化超参
的测试和打点数据
## 澄清
### history模块
主要和2 - 2.2 - 6~8相关，历史特性的设计目的是为了让模型在线回答时能够对新的未识别场景进行优化（这种情况下无法获得正确性反馈），因此第一次是原生思考之后按照某种规律压缩思维链，测试时反馈的依据是陌生验证集第一次到第n次的回答正确率不下降，可以将这一设计思路记录下来
### 过度设计
提前定义了大量生产抽象、动态增强和未来机制。结果是实施路径虽已从生产链路中解耦，文档的认知负担却还没有真正解耦。
1. 默认假设“必须有任务分类器”
当前流程隐含了：
    TaskView
    → SemanticTaskType
    → BudgetProfile
    → BudgetPlan
但真正需要预测的是 BudgetProfile，不一定需要中间的 SemanticTaskType。
例如，“规划”和“故障诊断”可能使用同一预算；同为“代码”任务的简单解释和复杂修复也可能需要不同预算。既然文档已经承认 semantic task 与 profile 并不一一对应，就没有必要让 semantic type 成为运行时必经实体。
更简单的路径是：
    可见请求特征
    → profile 或 reject
SemanticTaskType 可以保留为分析标签和报表维度，但不应成为阶段一自动策略的必要中间层。
2. PolicyBundle等已有对应实现think_budget_vllm_adapter/config的yaml->unified_config.py分级加载机制，不需要新增，没有必要绑定其他信息
3. 原则应是：能推导的字段不存储，只用于实验的字段不进入运行时模型。
阶段一最低只需要四类对象，且后两个对象只用于打点统计：
ScenarioSpec
CandidatePolicy
RouteResult          # 只有确认需要路由时才增加
ExperimentResult
存在若干重复状态：
   * confidence、top_score、margin 同时存在，但规则路由中的 confidence 很可能只是人为映射；
   * max_visible_think 已可由 check_length + num_thinking × think_stride 推导，不应再作为独立可写字段；
   * profile 的 status、revision 和 validation run IDs 可以放在候选 manifest，而不必进入运行时 dataclass。
4. 指标过多
建议阶段一只固化指标：
    唯一排序指标：
    产品场景等权宏平均 paired E2E gain
    两个硬门：
    1. 每场景及宏平均质量非劣
    2. 不新增 hard failure
    一个复杂度门：
    在收益近似时选择 profile 更少的方案
5. 阶段定义和安全原则重复过多
同一结论在多处重复：
两阶段边界：1.3、3.4、6.4、6.5、14；
native bypass：1.1、5.1、6.2、10.4、11、13、14；
history 推迟：1.2、3.4、4.5、5.7、6.5、7.2、8.3、11、14；
质量非劣：3.1、3.2、3.4、6.4、10.3、14；
hidden probe 必须计入：2.1、3.1、6.6、9、10、13、14。
这些重复并未增加新约束，反而使关键决策埋在长文中。建议每项原则只出现两次：
前部“不可违反的原则”；
最后“验收检查表”。
## 重构
### 统一task_type和scene
think_budget中存在设计错误，实际只需要一类信息（即任务分类），裁决统一使用scene标识，弃用task_type的一切实现
重构后的分类逻辑应该是：根据prompt匹配场景（scene），根据场景匹配budget
### 拒识门
使用恰当的字符串匹配算法来保证分类准确率（可离线检验：在tests中构造单元测试，使用docs/log/test_results中的具体问题抽样作为输入，测试分类效果）
## 采集
根据以上澄清与重构决策，修改think_budget_vllm_adapter源码，在服务运行时打印希望了解的信息以供后续泛化性优化决策
