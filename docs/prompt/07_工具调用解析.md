# DEBUG 工具解析问题
## 背景
AGENTS.md
启动参数 docs/debug/tool_call/start.sh
qwen3_coder tool_call_parser 源码 vllm/tool_parsers/qwen3coder_tool_parser.py
* 在 vllm/tool_parsers/__init__.py 中映射到 Qwen3CoderToolParser
* 核心标记在 Qwen3CoderToolParser.__init__() 中直接定义
* 非流式解析逻辑主要入口 extract_tool_calls
* Streaming 模式入口 extract_tool_calls_streaming 实际上是一个状态机
  * 它维护了不少状态
  * 开始阶段同时支持 token-id 和字符串检测
  * parameter 不是 token-by-token streaming，而是等 parameter 完整，然后一次构造一个较大的 delta 发出
  * 专门处理了 speculative decoding（# Process ALL complete params in a loop (spec decode fix).）
复现工具docs/debug/tool_call/test.py
### 问题现象
和流式tool_call_parser有关，即开启压缩后，工具调用部分有时未在tool_call中返回，不压缩则无问题
docs/debug/tool_call/chunks-4-fail.jsonl记录了一次失败的结果，7~23行的内容应当在tool_call键中返回，但实际在content键中
把日志里的 content 连起来，会发现缺少一段
```
<tool_call>
<
```
的内容，导致Qwen3CoderToolParser 的 streaming 状态机没有进入`self.is_tool_call_started = True`分支，之后状态就永远救不回来了。
也许这和DelegatingParser.parse_delta() 在同一个 delta 内先跑 reasoning parser；一旦发现 reasoning 结束，就把 reasoning 后面的 current_text/current_token_ids 重新交给 tool parser的行为有关
此外，注意到chunks-4-fail.jsonl的24-28行同样不符合逻辑，工具调用后模型的输出应当结束
### 概率复现
复现脚本自动化测试 JSONL 中的 request_body，检测流式返回是否有 tool_call 调用，并可选保存所有流式 chunk 到文件。
在启用思维链压缩时第4条请求有概率触发报错，大约5%
## 目标
定位问题根因并解决，保证开启压缩时工具调用部分不出错
从第一性原理出发，dtb（如流式and非流式透传实现）的设计目的是为了确保经过思维链压缩控制后，提交给下一环的输出从格式和逻辑上与原生模型一致，只是思考的长度变短了（更新到AGENTS.md中），但工具调用场景的现象却显示这一设计没有完整生效
### 建议
* 检查复现脚本的实现，提交多轮请求，记录工具调用的逻辑是否可靠，是否需要更多记录逻辑，可以为了debug方案改造或构建新的专用测试工具（建议实现在docs/debug/tool_call中）
* 检查think_budget_vllm_adapter对多轮请求的处理逻辑是否充分或与原始流程一致，过去的测试场景都是单论对话，这是一个盲点

* 基于以上输入，构建一个debug方案，指导应在服务器上如何执行，输出到docs/debug的新文档中
