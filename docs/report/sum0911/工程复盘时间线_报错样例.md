# 工程复盘时间线：报错样例与证据

配套：[可编辑的一页 PPT](工程复盘时间线_含报错示例.pptx)、[图片](工程复盘时间线_含报错示例.png)。本页整理时间为 2026-09-14，展示的工程排障时间范围仍为 2026-08-13 至 09-04。

## A. XML 泄漏与冗余 role

真实来源：[chunks-4-fail.jsonl](../../../tests/fixtures/tool_call/chunks-4-fail.jsonl)，物理第 7～26 行，响应 ID `chatcmpl-ae629356785c8aa0`。将 `delta.content` 按顺序拼接，可以看到：

```text
function=bash>
<parameter=command>
git checkout br_MAEV100R026C10_release
...
</function>
</tool_call>

user
<t
```

`...` 是展示省略，`\nuser\n<t` 在 PPT 中用转义写法显示实际换行。首个工具前缀 `<tool_call>\n<` 没有进入公开文本，工具 XML 进入 `content`；`user` 是正文中的角色尾流，不是新的合法 SSE role 字段。

修复处理了状态机回合边界和 text/token IDs 交接，工具 XML 由原生 parser 转成结构化 `tool_calls`。展示的是这一故障家族修复后的行为，不是声称对该请求执行过同文本生成的前后对照。

## B. tool delta 后继续输出 content

来源：[工具流排障文档 §2.1](../../debug/tool_call_streaming_debug_plan.md)。`run_after_fix` 的 100 条 DTB 中，50 条出现 tool delta 后继续 content；终止语义修复后的 100 条中该项为 0。

PPT 使用如下顺序示意，**不是逐字日志**，`[...]` 与 `"..."` 只是占位符：

```text
delta.tool_calls = [...]
delta.content = "..."
finish_reason = "tool_calls"
```

根因是旧控制器在 thinking 已进入工具阶段后继续 probe / fresh final，把第二段生成拼接进同一外部响应。修复后，模型边界触发同一逻辑 completion 的 continuation，最终源 terminal 保持正文、token IDs 和终止字段的绑定。一个回合仍允许多个合法工具调用。

## C. 参数 JSON 未闭合，却报告 tool_calls

真实来源：[run_server_01/summary.jsonl](../../log/perf/agent_tool_call_run04_paired_replay/run_server_01/summary.jsonl)，第 550 行，`client_request_id=dtbtool-l10-a5-dtb-run04-p0`。该响应的第二个工具 `index=1` 为：

```text
name: "write"
arguments: "{"
finish_reason: "tool_calls"
```

这些值来自归档 summary 对 SSE 的重组，排版省略了 id 等字段，不是完整 wire JSON。`invalid_argument_indexes=[1]`，第一个 `write` 的 arguments 已闭合；PPT 选取真实损坏的第二个工具，不沿用旧报告中“首个 write 缺括号”的描述。

更早的确定性分片证据见[排障文档 §2.1](../../debug/tool_call_streaming_debug_plan.md)：相同 955 字符的 raw text，在不同合法分片下形成 460/461 字符的 arguments，差异仅为末尾 `}`。该历史样本与上面第 550 行不是同一个请求。

工程处理包含两个不同层次：final 不再追加内部思考 stop，防止 XML 根本未生成完；工具 parser 在真实函数闭合后生成完整 canonical JSON，并处理同批连续调用。不能用补造括号修复模型未完成的 XML。

## D. 思考结束时吞掉正常尾句

真实来源：[replay2/RESULT.md §3.1](../../log/perf/agent_tool_call_run04_paired_replay/run_server_04_token_stop/replay2/RESULT.md)，`dtbtool-l5-a10-dtb-run04-token-stop-audit-01`。服务器 `server_filtered_part_01:2048`，公开 SSE `chunks.jsonl:373`，汇总 `summary.jsonl:19`。

```text
已有正文尾部   = "Let me try a"
delta_text    = " different approach.\n"
delta_token_ids = [2086, 5313, 13, 198, 248069]
stop_reason   = 248069
```

旧 reasoning parser 重放同一份输入，只保留到 `Let me try a`；修复后的服务器公开输出为：

```text
The task call format is problematic. Let me try a different approach.
```

这是同一输入的离线旧 parser 负对照与修复后实际公共输出的对比。末尾结构 stop token 的文字已剥离，ID 仍保留；修复保留同批正常正文，并维持 include-stop 默认 False。

## 补充：停止条件碰撞的显式 SSE error

来源：[run_server_03/RESULT.md §4](../../log/perf/agent_tool_call_run04_paired_replay/run_server_03/RESULT.md)，请求 `dtbtool-l10-a26-dtb-run04-targeted`。HTTP 200 之后仍可能收到错误事件：

```text
data: {"error":{"message":"DTB orchestration failed; see server logs",
       "type":"InternalServerError","param":null,"code":500}}
data: [DONE]
```

错误发生前，思考正文生成普通 token `</`=`510`、`think`=`26003`，与独立结构 token `248069` 不同。字符串 stop 与旧对齐假设碰撞，是由源码和 token 轨迹支持的根因解释；缺原始 traceback，不能把具体 RuntimeError 说成日志直接证明。流式 thinking 迁移为结构 token stop 后，定向回放未复现旧编排错误。

## 时间线和结果口径

- 8/13 的 98/100 是旧检查器检出值，另 2 条也存在跨 child 重复生成，不能当成正确请求。
- 8/14 role 尾流、tool 后 content 等计数为 0，随后前缀对齐使 XML 泄漏由 13/100 降至 0/100。两个回放阶段分别仍有 22/100、12/100 的其他异常。
- 8/17～19：180 对回放中，170 条含工具的 DTB 响应共 265 个调用，目标结构异常为 0；其余 10 条无工具响应中，8 条有 raw 支持模型未生成工具，2 条缺证据未分类。至少 49 条命中同批收尾，历史记录为真实 MTP 环境。
- 9/1：DTB 非法 JSON 由 133/300 降至 0/300，当轮仍有 DTB 1 条缺 terminal、Vanilla 2 条空参数，不能写成全部通过。来源：[run_server_02](../../log/perf/agent_tool_call_run04_paired_replay/run_server_02/RESULT.md)。
- 9/4：reasoning 丢字旧轮为 47/60，新轮为 0/60，两个 run 重新采样，不是同一批请求逐字恢复。新轮 48 个混合 chunk 的 344 字符全部保留，60/60 条 DTB 公开正文与 pre-parser 一致。两侧各 60 条，共 120 条工具流协议异常为 0。
- 三份版本化补丁为 `dtb_serving.patch`、`qwen3_coder_parser.patch`、`qwen3_reasoning_parser.patch`，对应固定 vLLM v0.23.0。
- 支持 MTP 表示兼容方案无需关闭投机解码，历史真实 MTP 回放覆盖了同批参数收尾。9/4 回放没有重新记录完整 MTP 启动身份，不能作为新的 MTP 性能实验。
- 9/4 结果是两条固定历史上下文的定向回放，DTB 均为短思考，没有覆盖 probe、迭代和强制截断全路径。任务语义和时延另行验收；本页不覆盖 9/4 之后的质量/性能进展。
